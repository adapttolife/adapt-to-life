# Adapt To Life

Marketing site for **Adapt To Life — Your Place in Adaptive Sports**, deployed on Cloudflare Workers. Serves a static site plus one form-capture API route.

- **Live:** https://adapttolife.org
- **Cloudflare Worker:** `adapt-to-life` (account: Alec@alecability.com)
- **Staging Worker:** `adapt-to-life-staging`, https://adapt-to-life-staging.adapt-to-life.workers.dev (its own script, never the production one)
- **Hosting model:** Workers with Static Assets — `public/` is served directly; `src/index.js` handles `POST /api/contact`.

## The forms → D1 → the Google Sheet

Every public form is saved durably in D1 before the visitor sees a success
(`form_submissions` + `form_deliveries`, see [`docs/durable-forms.md`](docs/durable-forms.md)).
From there, independent steps run:

| Form | Endpoint | What happens |
|---|---|---|
| `/contact` | `POST /api/contact` | Receipt to the sender, the original message to hello@, a shared intake record |
| `/apply` | `POST /api/apply` | Receipt to the applicant, a shared intake record (identity only; the full answers stay in D1) |
| `/volunteer/*` | `POST /api/volunteer` | Receipt to the volunteer, a shared intake record |

The Worker's 10-minute schedule notifies hello@ about every intake record still
waiting (`sweepIntake`), and Julia's hourly CRM refresh projects D1 into the
**Adapt To Life CRM** Google Sheet (Intake Register, Donations, Donor Reference).
The Sheet is the CRM. Nothing writes to Airtable (cut 2026-07-30) or ClickUp
(cut 2026-10-02).

The receipt emails promise every sender they will hear back, so an intake record
nobody has followed up is a broken promise, not a backlog.


The newsletter ("Join the list", `POST /api/subscribe`) adds the person to the Adapt To Life segment in Resend, records a shared intake row (so the signup reaches the CRM Intake Register) and starts the welcome series (`src/newsletter-series.js`). Beehiiv was dropped on 2026-11-07.

The Hustle & Heart Fund pages are `public/hustle-and-heart.html` (purpose and athlete context), `public/promise.html` (How Giving Works), and `public/apply.html` (eligibility, review, payment questions, and the application form → `POST /api/apply`). ## Deploy

To see which commit a URL serves, open `/build.json` on that same hostname
(production or staging). It contains the full
`commit`, `branch`, UTC `builtAt`, `dirty` flag, `assetDigest`, and a GitHub
`commitUrl`. `dirty: true` means local uncommitted changes were included, so the
commit alone does not reproduce that upload. `/build.txt` retains the compact
commit-and-digest format. Both endpoints disable caching and are generated by
the Wrangler build hook on each build; these files are not committed to Git.

This repository owns four deliberately separate Workers:

| Worker | Host | Entrypoint | Purpose |
|---|---|---|---|
| `adapt-to-life` | `adapttolife.org`, `www`, `sign` | `src/index.js` | Public site, forms, waivers, QR redirects |
| `adapt-to-life-staging` | `adapt-to-life-staging.adapt-to-life.workers.dev` only | `src/staging.js` | Staging (`env.staging`), deployed from the `staging` branch |
| `amelioration-reports` | `reports.amelioration.is` | `src/reports_worker.js` | Human report views behind Cloudflare Access |
| `amelioration-agent-mail` | `api.amelioration.is` | `src/agent_mail_worker.js` | Machine mail API plus inbound Email Worker events |

**Production ships from `main`, and only from `main`.** On 2026-09-10 the live build stamp
resolved to `fix/tim-mobile-framing` while `main` sat 272 commits behind without the homepage
hero — so every deploy started by working out what production actually was, and anyone branching
from `main` would have built against a site that did not exist. `scripts/guard-prod-branch.mjs`
now refuses a production deploy unless HEAD is `main`, the tree is clean, and `main` matches
`origin/main`. It runs from the `build` hook, so a bare `cfrun npx wrangler deploy` hits it too.
Staging is unguarded on purpose — it exists to look at a branch — and opts out through
`ATL_TARGET=staging`, which `deploy:staging` and `preview` set for you. Deploy staging only with `npm run deploy:staging`,
which refuses any branch but `staging`. A bare `wrangler deploy --env staging` skips that check:
the guard treats it as production, so it is refused off a clean, pushed `main`, and from `main`
it would put main's code on staging. Emergencies:
`ATL_ALLOW_UNSAFE_DEPLOY=<reason>`, which logs loudly.

The Cloudflare API token is injected at runtime from 1Password through `cfrun`; no secrets live in Git. Always name the intended deployment explicitly:

```sh
cfrun npm run deploy:prod
cfrun npm run deploy:reports
cfrun npm run deploy:agent-mail
```

`amelioration-agent-mail` accepts HTTP only on its custom domain, which is protected by a Cloudflare Access **Service Auth** policy. Access is the transport gate; the existing operator/per-agent bearer token remains mandatory inside the Worker and continues to enforce inbox ownership. Its `workers.dev` and preview hostnames must stay disabled. Inbound `*@agents.adapttolife.org` mail keeps the same address and DNS identity; Cloudflare Email Routing sends the event directly to this Worker and does not traverse the HTTP hostname.

### Staging is its own Worker

Staging deploys to `adapt-to-life-staging`, never to `adapt-to-life`. Until
2026-11-23 `env.staging` carried the production name, so every staging build
uploaded a version onto the production Worker. That afternoon a dashboard secret
edit on production deployed the newest uploaded version, which was the staging
build, and production ran staging code (fetch only, no scheduled or email
handler) for eleven minutes until main was redeployed.
`scripts/branch-preview.test.mjs` now fails if `env.staging.name` equals the
top-level name, and `npm run deploy:staging` refuses to run if it does.

| Command | What it does |
|---|---|
| `npm run preview` | Builds and tests the staging configuration with a wrangler dry run. Uploads nothing, on any branch. |
| `npm run deploy:staging` | The same, then `wrangler deploy --env staging` onto `adapt-to-life-staging`. Only from the `staging` branch. |
| `npm run deploy:ci` | Production's build command: deploys production on `main`, and only validates on any other branch. |

Staging has no routes and no custom domain. It answers only on
`https://adapt-to-life-staging.adapt-to-life.workers.dev`, which
`scripts/release.mjs` waits on before it releases. Never give staging a
production domain.

Workers Builds, one build per Worker:

| Worker | Production branch | Deploy command | Non-production branches |
|---|---|---|---|
| `adapt-to-life` | `main` | `npm run deploy:ci` | Version command `npm run preview` (build and test only); exclude `main` and `staging` |
| `adapt-to-life-staging` | `staging` | `npm run deploy:staging` | Off |

Build command is empty for both (Wrangler's build hook builds and tests) and the
root directory is the repository root. Merging into `main` requires the check
`Workers Builds: adapt-to-life-staging` on the release PR's head: that build
tested exactly the commit being released. Production's own build skips
`staging`, so requiring its check there would block every release. Pushing changes to `package.json` does not
update the commands saved in Cloudflare; change them in each Worker's
**Settings > Builds**.

The generated `public/css/` directory stays gitignored; the build hook builds it.
To identify what staging is actually serving, read its `/build.txt` and compare
the commit with the pushed commit.

Review previews go through the playground, not staging (see `AGENTS.md`). Only
the `staging` branch deploys, so one build at a time lands there.

Staging uses the live production databases. It is a copy for looking, not
for doing: it holds one secret, the Givebutter read key that fills the
fundraising total, so its pages match production. It has no mail, newsletter,
agent mail, report link, Body Shop contact or admin sign-in credentials, so
those routes fail closed there (no mail sent, no outside system written), and `src/staging.js` blocks the Givebutter webhook, the
newsletter sign-up and waiver signing outright. Adding a secret to staging
means production credentials on a second Worker that writes to production
data, so it needs the owner's yes. Forms still write to the shared databases;
test them on production or locally.

Staging exports only the HTTP handler and has an empty cron list. Production
continues to own scheduled jobs. Non-inherited Wrangler vars and bindings are
repeated under `env.staging`; keep their service settings aligned with production.
Secrets are set on the `adapt-to-life-staging` Worker itself (it no longer
inherits production's), never in committed vars. Production has
`preview_urls: false`: nothing should run on production bindings except
production.

Every wrangler invocation stamps `public/build.txt` through the `build` hook in `wrangler.jsonc`,
including a bare `cfrun npx wrangler deploy`, and `check-site.mjs` fails if the build it reaches is
not the build you are testing. The hook is not in an npm script because a second session deployed
production with bare wrangler 19 seconds after ours and the stamp went missing: a control a human
has to remember to invoke is not a control. That check is the point: it is what turns "someone deployed over
me" from a thing you find out from Alec into a thing the harness tells you.

Preview locally without deploying:

```sh
npx wrangler dev
```

## Checking a deploy

```sh
node scripts/check-site.mjs <your-preview-url>       # a playground preview
node scripts/check-site.mjs                          # staging (adapt-to-life-staging)
node scripts/check-site.mjs https://adapttolife.org  # prod, after promoting
```

Run it after every deploy. It clicks rather than greps: every page returns 200 and an unknown
path 404s, the mobile menu opens on one tap, the desktop dropdown opens on click, the mobile
and desktop navs list the same items, there is no horizontal overflow at 390px or 1440px, no
reachable dead links, and no console errors. It exists because `/popcorn` once shipped with the
nav script included twice, so every tap toggled the mobile menu open and shut and the menu never
opened. The markup was identical on every page and grepping it found nothing.

Edge propagation runs ~35 to 60 seconds. Poll the served HTML for a string from your change
before trusting a check or a screenshot, or you will verify the previous build.

## Handing an iteration over

`/review` has ONE writer per branch and two concurrent branches will both rewrite it. That is fine
and it is not worth coordinating: resolve the conflict in favour of the branch that merges last,
because the file means "the newest iteration". Review happens on your own preview URL, so the
shared path never has to arbitrate between two live iterations.

`/review` is the one link a reviewer gets: a single ordered walk of what changed, staging-only
(production 302s it home). It is part of the work, not a chore afterwards, so **update
`public/review.html` in the same commit as the iteration.** Give it the stops in the order a
visitor would walk them, one line each on what changed, plus what specifically to look at and
what is deliberately unfinished, so nobody spends attention reporting known gaps.

`check-site.mjs` fails if the tour's `updated` stamp predates the newest change under `public/`,
or if it links to a page that no longer resolves. It went stale once and the person reviewing
had to ask twice for a usable link.
